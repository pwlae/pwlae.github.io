How to use this guide

This guide is for people who learn on the way to work. One lesson fits one commute: about 10 minutes of reading, then a few small LeetCode problems.

The idea

You get better at algorithms by solving many easy problems quickly, not by spending three days on one hard problem. Each solved problem is a small win, and the small wins add up.

So every lesson works the same way:

  1. Read the idea. Short, plain words, one picture.
  2. See it in Python. One small piece of code you can reuse.
  3. Solve 3–6 problems on LeetCode, easiest first. Each one has a time box.

The 15-minute rule

Your commute ends whether you finished or not. If you think too long, you lose the thread by the next train. So:

  • Stuck for 15 minutes? Open the Hint.
  • Stuck 5 minutes after that? Open the Solution. Read it, close it, and type it in LeetCode yourself. This still counts. You learned the trick.
  • Tomorrow, solve that problem again from memory. It should take a few minutes.

Move to the next lesson when the easy problems feel quick, about 10 minutes each. You do not need to be perfect.

Python toolkit for LeetCode

Read first: How to use this guide

Before any algorithm, you need a few Python tools you will use in almost every problem: lists, loops, dictionaries and sets. This lesson is the toolbox.

What a LeetCode answer looks like

LeetCode gives you a class with one method. You fill in the method and return the answer. You never read input or print output yourself.

class Solution:
    def getConcatenation(self, nums: List[int]) -> List[int]:
        return nums + nums

nums: List[int] is only a label: "nums is a list of whole numbers". -> List[int] says what you return. Python does not check these labels. They are there to help you read.

Lists: a row of boxes

A list is a row of boxes. Each box has a number called its index, starting from 0. In the picture, the index is on top and the value below it.

nums = [7, 2, 9, 4]
nums[0]        # 7, the first box
nums[-1]       # 4, the last box
len(nums)      # 4 boxes
nums[1:3]      # [2, 9], from index 1 up to (not including) 3
nums.append(5) # add a box at the end -> [7, 2, 9, 4, 5]

Loops: visit every box

Most easy problems are "walk through the list once and keep track of something".

for x in nums:                 # just the values
    print(x)

for i in range(len(nums)):     # just the indexes 0, 1, 2, ...
    print(i, nums[i])

for i, x in enumerate(nums):   # both at once (usually the nicest)
    print(i, x)

Handy built-ins

sum(nums)              # add everything up
max(nums), min(nums)   # biggest, smallest
sorted(nums)           # a new sorted list, nums stays the same
[x * 2 for x in nums]  # a new list built from nums ("list comprehension")

Dictionaries: labelled boxes

A dictionary (dict) stores key → value pairs, like a phone book. Looking up a key is instant. You do not search through everything.

age = {"ann": 31, "bob": 25}
age["ann"]               # 31
age["cat"] = 40          # add or change
"bob" in age             # True
age.get("dan", 0)        # 0 if "dan" is missing (no error)

count = {}
for word in ["a", "b", "a"]:
    count[word] = count.get(word, 0) + 1   # {"a": 2, "b": 1}

Sets: "have I seen this?"

A set keeps each value once, and checking "is it in there?" is instant.

seen = set()
seen.add(3)
3 in seen          # True
len(set([1, 1, 2]))  # 2, duplicates are dropped

Interesting fact: Why append is fast

A Python list asks for a bit more memory than it needs, about 12% extra. Most append calls then just fill a spare box. Only now and then does the list move to a bigger block of memory. Java's ArrayList, C++'s std::vector and Go's slices use the same trick, so adding to the end is cheap on average in all of them.

Big O in plain words

Read first: Python toolkit for LeetCode

Big O is a short way to say how much slower your code gets when the input gets bigger. You need it to tell whether your answer will pass on LeetCode before you even press Submit.

The idea

Imagine your input grows from 1,000 items to 1,000,000. Does your code take the same time? A thousand times longer? A million times longer? Big O answers that question, and ignores small details like "this line runs twice".

Here are the five you will meet most, with everyday pictures:

  • O(1), constant. Opening locker number 42. It takes the same time with 10 lockers or 10,000.
  • O(log n), logarithmic. Finding a name in a paper phone book by opening it in the middle, then the middle of the half you need, and so on. Doubling the book adds just one more step.
  • O(n), linear. Walking down a train carriage checking every seat. Twice the seats, twice the time.
  • O(n log n). Good sorting. A bit more than linear, still fast.
  • O(n²), quadratic. Everyone at a party shakes hands with everyone else. Twice the people, four times the handshakes.

"n" just means "how big the input is", usually the length of the list or string.

Steps for n = 1,000,000, fastest at the top. Python does very roughly 10 million simple steps a second.

How to spot it in Python

You don't need maths. Look at the shape of the code:

nums[5]                 # O(1): jump straight to a box
x in some_set           # O(1): sets and dicts look up instantly
x in some_list          # O(n): checks the boxes one by one

for x in nums:          # one loop over n items: O(n)
    total += x

for a in nums:          # a loop inside a loop: O(n²)
    for b in nums:
        if a + b == 10:
            count += 1

sorted(nums)            # O(n log n)

Watch out for hidden loops: x in some_list, nums.index(x), nums.count(x) and slicing nums[a:b] all walk through the list. Put one inside a for loop and you have O(n²) without seeing two loops.

Memory counts too

Big O also describes extra memory ("space"). Keeping a few variables like total or best is O(1) space. Building a new list or set as big as the input is O(n) space. Often you trade memory for speed: a set costs O(n) memory but turns O(n) lookups into O(1).

Will my answer pass?

Every LeetCode problem lists limits like 1 <= nums.length <= 10^4. Use them as a quick check before you code:

Biggest nWhat is usually fast enough
up to about 1,000O(n²) is fine
up to about 10,000O(n²) is borderline in Python. Try for better
100,000 or moreyou need O(n log n) or O(n)

So if n is small, the simple double loop is a perfectly good answer. Don't make it clever when it doesn't need to be.

Worked example

"Count how many numbers in the list are smaller than each number." The simple way compares every pair:

result = []
for a in nums:              # n times...
    smaller = 0
    for b in nums:          # ...n times each
        if b < a:
            smaller += 1
    result.append(smaller)
# n × n comparisons: O(n²) time, O(n) space for the result

If the list has 500 numbers, that's 250,000 comparisons: instant. With 1,000,000 numbers it's a million million: far too slow. The problem's limits tell you which world you are in.

Interesting fact: When the worst case is an attack

A Python dict is O(1) on average, but if many keys land on the same shelf it slows down to O(n). In 2003, researchers Scott Crosby and Dan Wallach showed that attackers could pick keys on purpose to make that happen. In 2011 the same trick was shown to freeze web servers in PHP, Java, Ruby and Python by sending one form full of carefully chosen field names.

Python's fix was to add a random secret to its string hashing, chosen fresh every time Python starts. It is on by default since Python 3.3, so attackers can no longer guess which keys collide.

Remember

  • Big O = how the work grows as the input grows. Common ones, fast to slow: O(1), O(log n), O(n), O(n log n), O(n²).
  • One loop is O(n), a loop inside a loop is O(n²), and in list hides a loop. in set doesn't.
  • Read the limits first: small n means the simple answer is fine.

Arrays: one loop does a lot

Read first: Big O in plain words

A surprising number of easy problems are solved by walking through the list once and keeping one or two numbers up to date as you go. This lesson teaches that habit.

The idea

Picture yourself walking down a long train, counting passengers. You don't write down every seat. You just keep a running total in your head, and maybe remember "the fullest carriage so far". When you reach the end, you have your answer.

That is the single scan:

  1. Before the loop, set up a few variables: the current thing you're tracking, and the best answer so far.
  2. For each item, update current.
  3. Then compare: if current beats best, update best.
  4. After the loop, return best.

In Python

def scan(nums):
    best = 0          # the answer so far
    current = 0       # what we are tracking right now
    for x in nums:
        current = ...              # update using x
        best = max(best, current)  # keep the best one seen
    return best

It visits each item once, so it is O(n) time. It only keeps a couple of variables, so it is O(1) extra space. You can't do much better than that.

Worked example

Longest run of 1s in [1, 1, 0, 1, 1, 1]:

xcurrentbest
111
122
00 (reset)2
112
122
133

Answer: 3. Notice that best is updated inside the loop, every time. If you only update it when you see a 0, you forget the last run, which is the most common slip-up.

Two traps

  • Starting values. best = 0 is fine when answers can't be negative. If they can, start with best = float('-inf') (smaller than any number) or with the first item, nums[0].
  • What "current" means. Say it in words before you code: "the length of the run of 1s ending here", "the lowest price so far". Once the sentence is clear, the update line is easy.

LeetCode121. Best Time to Buy and Sell Stock
Easy ~15 min☐ solved · https://leetcode.com/problems/best-time-to-buy-and-sell-stock/
Hint
Walk through the days. Keep the lowest price so far (the best day to have bought). On each day, ask: "if I sold today, what would I make?"
Solution
class Solution:
    def maxProfit(self, prices: List[int]) -> int:
        lowest = float('inf')   # cheapest price seen so far
        best = 0                # best profit so far (0 = don't trade)
        for p in prices:
            lowest = min(lowest, p)
            best = max(best, p - lowest)   # sell today?
        return best
# One pass: O(n) time, O(1) space. Two nested loops would be O(n²),
# too slow for 100,000 prices.
Interesting fact: Why computers love walking through arrays

Memory is slow compared with the processor. So when a CPU reads one number from memory, it actually fetches a whole block around it (a cache line, usually 64 bytes) and keeps it close by. When the CPU notices you are reading in order, it starts fetching the next blocks before you ask.

That's why a plain left-to-right scan over numbers stored side by side is one of the fastest things a computer can do. It's a big reason NumPy and databases like DuckDB store columns of numbers next to each other.

Remember

  • Single scan: one loop, a current value and a best value. O(n) time, O(1) space.
  • Update best on every step, not only at the "end" of something.
  • Say what current means in words first. Use float('-inf') / float('inf') as safe starting values.

Strings

Read first: Arrays: one loop does a lot

A string is a row of characters, so almost everything you learned about lists works on strings too. This lesson adds the few string-only rules and tools you need for LeetCode.

The idea

Think of a string as a row of letter tiles, like in Scrabble. Each tile has an index, starting from 0, just like a list.

s = "hello"
s[0]        # "h"
s[-1]       # "o"
len(s)      # 5
s[1:4]      # "ell"
s[::-1]     # "olleh", reversed
for ch in s:
    print(ch)   # h, e, l, l, o

There is one big difference from lists: you can't change a string. s[0] = "H" is an error. Strings are immutable ("unchangeable"). Every "change" actually builds a brand-new string.

Build a list, then join

Because every change makes a new string, gluing letters on one at a time with += can copy the whole string again and again. The safe habit: collect the pieces in a list, then glue them once with "".join(...).

With s += ch, every step makes a new copy:

With a list and join, you collect the pieces and copy once at the end:

pieces = []
for ch in "hello":
    pieces.append(ch.upper())
result = "".join(pieces)    # "HELLO"

For short strings either way is fine. For long ones, the list-then-join way is reliably O(n).

Handy string tools

"a,b,c".split(",")       # ["a", "b", "c"]
"  hi  ".strip()          # "hi" (removes spaces at both ends)
"Hello".lower()           # "hello"
"a.b".replace(".", "!")   # "a!b"
"abc".isalpha()           # True: only letters?
"123".isdigit()           # True: only digits?
"-".join(["a", "b"])      # "a-b"

Characters are numbers underneath

Every character has a number code. ord turns a character into its number, and chr turns it back. Letters are in order, so you can do maths with them:

ord("a")        # 97
ord("b")        # 98
chr(97)         # "a"
ord("A")        # 65, capitals come 32 before lowercase

ord("c") - ord("a")   # 2: "c" is letter number 2 (counting from 0)

LeetCode709. To Lower Case
Easy ~5 min☐ solved · https://leetcode.com/problems/to-lower-case/
Hint
s.lower() is one line. By hand: for each character, if it is between "A" and "Z", add 32 to its ord and turn it back with chr.
Solution
class Solution:
    def toLowerCase(self, s: str) -> str:
        pieces = []
        for ch in s:
            if "A" <= ch <= "Z":
                ch = chr(ord(ch) + 32)   # "A" (65) -> "a" (97)

Hash maps and sets

Read first: Strings

This is the most useful trick in easy LeetCode: spend a little memory to remember what you've seen, so you never have to search for it again. In Python that means a set or a dict.

The idea

Think of a theatre cloakroom. You hand over your coat and get ticket number 37. When you come back, the attendant doesn't search through every coat. They go straight to hook 37. Finding your coat takes the same time whether there are 10 coats or 1,000.

A hash table works the same way. A hash function turns any key (a word, a number) into a hook number, and the value is stored on that hook. To look something up, Python recomputes the hook number and goes straight there.

Sometimes two keys get the same hook (a collision). Python handles that for you, and on average a lookup still takes O(1).

Python gives you two hash tables:

  • set answers "have I seen this?"
  • dict answers "what do I know about this?" (where I saw it, how many times…)

In Python

seen = set()
seen.add(4)
4 in seen               # True, O(1)

where = {}              # value -> index
where[10] = 0
10 in where             # True, O(1): checks keys
where[10]               # 0
where.get(99)           # None instead of an error

Keys must be things that can't change: numbers, strings and tuples work. Lists can't be keys (use tuple(my_list) if you need to).

The big trick: one pass instead of two loops

Many problems ask "is there a pair that…?". The obvious answer checks every pair with two loops: O(n²). The hash-table answer walks the list once, and for each number asks the set or dict "have I already seen the partner I need?". That's O(n) time, paid for with O(n) memory.

seen = set()
for x in nums:
    if partner_of(x) in seen:   # O(1) lookup instead of a second loop
        ...found it...
    seen.add(x)

Counting things

Read first: Hash maps and sets

Lots of problems become easy once you know how many times each thing appears. Build that tally first, then answer the question from the tally.

The idea

Picture a teacher counting votes on the board: one tick next to a name for every vote. When counting is done, questions like "who won?", "did anyone get exactly one vote?" or "did two people tie?" are answered just by looking at the board.

In code, the board is a dict from item to count, often called a frequency map.

In Python

By hand, with the .get(key, 0) trick from the toolkit lesson:

count = {}
for ch in "banana":
    count[ch] = count.get(ch, 0) + 1
# {'b': 1, 'a': 3, 'n': 2}

Python has a ready-made tool for this, Counter. It is a dict with extras:

from collections import Counter

count = Counter("banana")   # Counter({'a': 3, 'n': 2, 'b': 1})
count["a"]                  # 3
count["z"]                  # 0, missing keys count as 0 (no error)
count.most_common(1)        # [('a', 3)], the top item
Counter("listen") == Counter("silent")   # True: same letters, same counts

Building the tally is one pass: O(n) time, and O(k) space where k is the number of different items. On LeetCode, Counter is already imported for you.

Two passes: count, then look

The usual shape is two loops one after the other (not one inside the other, so still O(n)):

  1. Pass 1: build the counts.
  2. Pass 2: go through the input (or the counts) again and answer the question.

For example, "first letter that appears only once": pass 1 counts every letter, pass 2 walks the word in order and returns the first letter whose count is 1.

Shortcut for letters only

If the input is only lowercase letters a to z, you can use a list of 26 zeros instead of a dict. The letter's position is ord(ch) - ord("a") (from the Strings lesson):

count = [0] * 26
for ch in "banana":
    count[ord(ch) - ord("a")] += 1
# count[0] is "a": 3,  count[1] is "b": 1,  count[13] is "n": 2

Two pointers

Read first: Arrays: one loop does a lot, Strings

Instead of one loop variable, use two indexes that move through the list together. This turns many "check every pair" problems into a single pass, and often needs no extra list at all.

The idea

There are two flavours. Learn both, because they come up everywhere.

1. Opposite ends, walking inwards. Picture two people starting at opposite ends of a train platform and walking towards each other, comparing what they see, until they meet in the middle. That's how you check whether a word reads the same backwards:

2. Slow and fast, same direction. One pointer (read) visits every item. The other (write) only moves when you keep an item. Everything to the left of write is "the answer so far". It's like tidying a bookshelf in one pass: you look at every book, but only the keepers get pushed to the front.

In Python

# Flavour 1: opposite ends
left, right = 0, len(nums) - 1
while left < right:
    # look at nums[left] and nums[right], then move one or both
    left += 1
    right -= 1

# Flavour 2: slow (write) and fast (read)
write = 0
for read in range(len(nums)):
    if keep(nums[read]):
        nums[write] = nums[read]
        write += 1
# nums[:write] now holds the kept items

Each pointer only moves forward (or only backward), so together they take at most n steps: O(n) time. They change the list where it is ("in place"), so O(1) extra space.

Worked example: Move Zeroes

Push all zeros in [0, 1, 0, 3, 12] to the end, keeping the other numbers in order. read walks every item. When it finds a non-zero, swap it into position write and move write on.

Sliding window

Read first: Two pointers, Hash maps and sets

When a problem asks about a stretch of neighbouring items ("the best 4 days in a row", "the longest piece of text without repeats"), don't re-add the whole stretch every time. Slide a window along and update it a little at each step.

The idea

Imagine you're on a train and the window shows exactly 4 houses at a time. When the train moves one house forward, one new house appears at the front and one old house disappears at the back. The other three are still there. You don't have to look at them again.

A sliding window is a stretch of the list from index left to index right. It comes in two kinds:

  • Fixed size: always k items. Each step: add the item coming in, remove the item going out.
  • Growing and shrinking: the right edge moves forward every step. The left edge moves forward only when the window breaks a rule (for example, "no repeated letters").

Fixed-size window

Best sum of 4 neighbours in [1, 12, -5, -6, 50, 3]:

Re-adding 4 numbers for every position would be O(n·k). Updating with one add and one subtract is O(n).

window = sum(nums[:k])             # the first window
best = window
for right in range(k, len(nums)):
    window += nums[right]          # item coming in
    window -= nums[right - k]      # item going out
    best = max(best, window)

Growing and shrinking window

Here the window has a rule, and you keep it as big as you can while the rule holds. A set or dict remembers what is inside the window.

left = 0
inside = set()
best = 0
for right, x in enumerate(items):
    while x in inside:          # adding x would break the rule...
        inside.remove(items[left])
        left += 1               # ...so shrink from the left until it's OK
    inside.add(x)
    best = max(best, right - left + 1)   # window length

It looks like a loop inside a loop, but left only ever moves forward, so it moves at most n times in total. Overall it's still O(n). That's the two-pointers idea again.

Prefix sums

Read first: Arrays: one loop does a lot

If you need the sum of many different stretches of a list, add things up once in advance. After that, the sum of any stretch is a single subtraction.

The idea

Think of your contactless or Oyster card history, which shows your total spent so far after each journey. How much did journeys 4 to 7 cost? You don't add up those four fares. You take "total after journey 7" minus "total after journey 3". Done.

A prefix sum list stores exactly that: the running total up to each position. You met it already in the toolkit lesson as Running Sum.

The trick that avoids special cases is to start the list with a 0 ("total before anything"). Then prefix[i] is the sum of the first i numbers:

Now the sum of nums[left] up to and including nums[right] is:

prefix[right + 1] - prefix[left]

Example with nums = [3, 1, 4, 1, 5]: the sum of indexes 1 to 3 is 1 + 4 + 1 = 6, and the formula gives prefix[4] - prefix[1] = 9 - 3 = 6. ✓

In Python

prefix = [0]
for x in nums:
    prefix.append(prefix[-1] + x)   # previous total + this number
# prefix has len(nums) + 1 items

def range_sum(left, right):         # inclusive on both ends
    return prefix[right + 1] - prefix[left]

Building the list is one pass: O(n) time and O(n) space. Every range sum after that is O(1). Without it, each range sum would loop over the range: O(n) each time.

Left side and right side

Some problems ask about "everything to the left of i" and "everything to the right of i". You don't even need the whole prefix list, just the total and a running left sum:

total = sum(nums)
left_sum = 0
for i, x in enumerate(nums):
    right_sum = total - left_sum - x   # everything after i
    # ...compare left_sum and right_sum here...
    left_sum += x                      # now includes nums[i]

Stack

Read first: Strings

A stack is a pile where you only touch the top. It's the right tool whenever the most recent unfinished thing is the one you need next: matching brackets, undo, "cancel the last one".

The idea

Think of a stack of plates in a canteen. You put a clean plate on top, and you take a plate from the top. You never pull one out of the middle. The last plate in is the first plate out ("last in, first out").

Three operations, all instant:

  • push: put something on top
  • pop: take the top thing off
  • peek: look at the top without taking it

In Python

A plain list is already a stack. The end of the list is the top.

stack = []
stack.append(3)     # push -> [3]
stack.append(7)     # push -> [3, 7]
stack[-1]           # peek -> 7
stack.pop()         # pop  -> 7, stack is [3] again
if stack:           # is it non-empty? (pop on an empty list is an error)
    ...

append, pop() and [-1] are all O(1). Avoid pop(0), which takes from the bottom and is slow (that's a queue, next lesson).

When to think "stack"

  • Things come in pairs that nest, like ( [ ] ): the most recent opener must close first.
  • A new item can cancel the previous one, like "undo" or deleting the last character.
  • You need "the most recent item that is still waiting for something".

Worked example: matching brackets

Is "({[]})" correctly matched? Push every opener. On a closer, the top of the stack must be its partner: pop it. At the end, the stack must be empty.

It fails if a closer arrives when the stack is empty, if the top is the wrong opener, or if anything is left at the end.

Queue and deque

Read first: Stack

A queue is the fair line: whoever arrived first is served first. You'll use it to handle things in the order they came in, and later it powers breadth-first search on trees and graphs.

The idea

Think of the queue at a ticket barrier. New people join at the back. The person at the front goes through next. Nobody pushes in. That's "first in, first out", the opposite of a stack (where the newest item leaves first).

Items move down the line: join at the back, leave from the front.

In Python: use deque

You could use a list with pop(0), but that's slow. Removing the first item makes every other item shift one place left, which is O(n). Use collections.deque ("deck", short for double-ended queue) instead. Adding or removing at either end is O(1).

from collections import deque

q = deque()
q.append(4)       # join at the back  -> deque([4])
q.append(7)       #                   -> deque([4, 7])
q.append(2)       #                   -> deque([4, 7, 2])
q[0]              # peek at the front -> 4
q.popleft()       # leave from front  -> 4, now deque([7, 2])
len(q)            # 2
if q:             # non-empty?
    ...

# Both ends work, so a deque can also act as a stack:
q.appendleft(9)   # -> deque([9, 7, 2])
q.pop()           # -> 2, from the back

On LeetCode, deque is already imported.

When to think "queue"

  • Things must be handled in arrival order: requests, tasks, messages.
  • You keep only recent items: drop old ones from the front while they're too old.
  • You explore level by level (nearest first). That's breadth-first search, coming in the trees and graphs lessons.

Worked example: the last 3,000 milliseconds

Count how many requests arrived in the last 3,000 ms. Each new time joins at the back. Then, while the front is older than t - 3000, drop it. What's left is exactly the recent window.

LeetCode232. Implement Queue using Stacks
Easy ~15 min☐ solved · https://leetcode.com/problems/implement-queue-using-stacks/
Hint
Use two stacks (lists): inbox for pushes, outbox for pops. When outbox is empty and you need the front, pour everything from inbox into outbox. Pouring reverses the order, so the oldest item ends up on top.
Solution
class MyQueue:
    def __init__(self):
        self.inbox = []
        self.outbox = []

    def push(self, x: int) -> None:
        self.inbox.append(x)

    def _refill(self):
        if not self.outbox:
            while self.inbox:              # reversing puts the oldest on top
                self.outbox.append(self.inbox.pop())

    def pop(self) -> int:
        self._refill()
        return self.outbox.pop()

    def peek(self) -> int:
        self._refill()
        return self.outbox[-1]

    def empty(self) -> bool:
        return not self.inbox and not self.outbox
# Each item is moved at most once, so every operation is O(1) on average.

Interesting fact: How Python's deque stays fast at both ends

A Python list is one long row of boxes, so removing from the front means shifting everything. A deque is built differently: a chain of small blocks of 64 slots each, linked together. Adding at either end just fills the next free slot in the first or last block, or links on a new block when that one is full. Nothing ever shifts.

Job queues and message brokers that pass work between computers (such as RabbitMQ) are built around the same first-in, first-out promise.

Linked lists

Read first: Two pointers

A linked list is a chain of small boxes, where each box knows only where the next one is. Most linked-list problems are about walking that chain carefully and re-pointing arrows without losing anything.

The idea

Think of a treasure hunt. Each note has a clue (the value) and says where the next note is hidden. To reach note 5 you can't jump there. You have to follow notes 1, 2, 3, 4. The last note says "the end".

Each box is called a node. It holds a val and a next arrow pointing to the following node. The last node's next is None. The first node is the head, and you're usually given just that.

In Python

LeetCode gives you this class (it's shown in a comment above your code):

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

# walking the whole list: O(n)
node = head
while node:              # stops after the last node (node becomes None)
    print(node.val)
    node = node.next

Compared with a Python list: adding or removing a node once you're standing next to it is O(1), just re-point arrows. But finding the 5th node is O(n), because you have to walk there.

Three tricks

1. Dummy head. When building a new list, start with a fake node, so you never need a special case for "the list is still empty". Return dummy.next at the end.

dummy = ListNode()
tail = dummy
for v in [4, 5, 6]:
    tail.next = ListNode(v)   # attach a new node
    tail = tail.next          # move to the new end
return dummy.next             # skip the fake node

2. Fast and slow pointers. From the two-pointers lesson: slow moves 1 step, fast moves 2. When fast hits the end, slow is in the middle. And if the list loops back on itself, fast will eventually lap slow, like a faster runner on a track. That's how you detect a cycle.

3. Save before you re-point. Changing node.next throws away the old arrow. If you still need the rest of the list, save it in a variable first.

Worked example: reverse a list

Turn 1 → 2 → 3 into 3 → 2 → 1. Walk the list, flipping each arrow to point backwards. Three variables: prev (the already-reversed part), cur (the node we're flipping), and nxt (trick 3: the rest, saved before we flip).

prev, cur = None, head
while cur:
    nxt = cur.next      # save the rest
    cur.next = prev     # flip the arrow
    prev = cur          # step forward
    cur = nxt
return prev             # the old last node is the new head

Binary search

Read first: Big O in plain words, Arrays: one loop does a lot

Binary search finds something in a sorted list by looking at the middle and throwing away the half that can't hold the answer. A million items take about 20 looks instead of a million.

The idea

Play "guess my number" from 1 to 100. A friend only says "higher" or "lower". The smart first guess is 50. If they say "lower", every number from 50 to 100 is gone in one go. Next guess 25, then 12 or 37, and so on. Each guess cuts what's left in half, so you never need more than 7 guesses (2 × 2 × 2 × 2 × 2 × 2 × 2 = 128, which covers 100).

On a list it works the same way. Keep two markers: lo (the left end of the part still in play) and hi (the right end).

  1. Look at the middle item, mid.
  2. Is it the target? Done.
  3. Too small? The answer is to the right: move lo to mid + 1.
  4. Too big? The answer is to the left: move hi to mid - 1.
  5. If lo passes hi, nothing is left: the target isn't there.

Here is a search for 9 in [1, 3, 5, 7, 9, 11, 13] (indexes 0 to 6):

The catch: this only works when the list is sorted. "Too small, so go right" is only true if everything to the right is bigger. It also works on anything with a single switch point: a row of answers that go "no, no, no, yes, yes, yes". You can binary search for the first "yes".

In Python

One template. Learn it once and use it for every problem in this lesson.

def binary_search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:   # still in play
        mid = (lo + hi) // 2  # middle
        if nums[mid] == target:
            return mid
        elif nums[mid] < target:
            lo = mid + 1  # go right
        else:
            hi = mid - 1  # go left
    return -1  # lo passed hi

Each loop throws away half of what's left, so the cost is O(log n) time (see Big O) and O(1) extra space.

Variant: find the first "yes"

Sometimes you don't want an exact match. You want the first place where something becomes true: the first bad version, the first number ≥ target. Two small changes: loop while lo < hi, and when mid is a "yes", keep it with hi = mid (it might be the answer).

def first_yes(lo, hi, is_yes):
    while lo < hi:
        mid = (lo + hi) // 2
        if is_yes(mid):
            hi = mid      # keep mid
        else:
            lo = mid + 1  # skip mid
    return lo  # lo == hi: first yes

Python has this built in. bisect.bisect_left(nums, x) returns the first index where nums[i] >= x, which is where x would go to keep the list sorted.

import bisect
bisect.bisect_left([1, 3, 5, 7], 5)  # 2
bisect.bisect_left([1, 3, 5, 7], 4)  # 2

Both give 2: 5 is at index 2, and 4 would also go at index 2, just before the 5.

Sorting

Read first: Binary search

Sorting puts things in order: smallest to biggest, A to Z. In Python it's one line, and "sort it first" turns many hard-looking problems into easy ones.

The idea

Imagine a pile of exam papers to put in order by name. A smart way: split the pile in half and give each half to a friend. They split theirs again, and so on, until everyone holds one paper (one paper is always "sorted"). Then everyone hands back up: two sorted piles become one sorted pile, by always taking the smaller top paper. That is merge sort.

  1. Split the list in half, again and again, until each piece has one item.
  2. Merge pairs of sorted pieces back into one sorted piece.
  3. Keep merging until one piece is left: the whole list, sorted.

The merge step is two pointers: one finger on each sorted piece. Compare the two items under your fingers, take the smaller one, move that finger. Merging [2, 5] and [1, 4]:

Halving takes about log n levels, and each level touches all n items once. So merge sort costs O(n log n), much faster than O(n²) for big lists.

You'll hear other names. Bubble sort and insertion sort are simple but O(n²). Quicksort picks a "pivot" and splits around it, usually O(n log n). You don't need to learn them now.

In Python

In real code and on LeetCode, don't write your own sort. Use the built-in one. It's O(n log n) and very well tested.

nums = [5, 2, 4, 1]
sorted(nums)  # new list [1, 2, 4, 5]
nums.sort()   # sorts nums itself
sorted(nums, reverse=True)  # 5 4 2 1

# key=: sort by something you compute
words = ["pear", "fig", "banana"]
sorted(words, key=len)
# fig, pear, banana

# Tuples sort by the first item,
# then the second on a tie
pairs = [(2, "b"), (1, "z"), (2, "a")]
sorted(pairs)  # (1,z) (2,a) (2,b)

# lambda: a tiny one-line function
people = [("Ann", 31), ("Bob", 25)]
people.sort(key=lambda p: p[1])  # age

Python's sort is stable: items that tie keep their old order. Extra space is O(n) in the worst case.

"Sort first" as a move

When a problem feels messy, ask: would it be easy if the list were sorted? Sorting costs O(n log n), and afterwards:

  • Equal items become neighbours. Duplicates are next to each other, so one scan finds them.
  • Two pointers work. On two sorted lists you can walk both at once, like the merge above.
  • Intervals line up. Sort meetings by start time and overlaps sit side by side.
  • Binary search works. See Binary search.

One more trick. If the values are small whole numbers (say 1 to 100), you can sort by counting: count how many 1s, 2s, 3s… there are, then write them out in order. That's counting sort, O(n + k) where k is the range of values.

    def intersection(self, nums1: List[int],
                     nums2: List[int]) -> List[int]:

        out = []

                if not out or out[-1] != a[i]:

                j += 1

                i += 1  # smaller moves
            else:
                j += 1
        return out

class Solution:
    def sortArray(self, nums: List[int]) -> List[int]:
        if len(nums) <= 1:
            return nums  # already sorted
        mid = len(nums) // 2
        left = self.sortArray(nums[:mid])
        right = self.sortArray(nums[mid:])
        return self.merge(left, right)

    def merge(self, left, right):
        out = []
        i = j = 0
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:  # <= keeps it stable
                out.append(left[i])
                i += 1
            else:
                out.append(right[j])
                j += 1
        out.extend(left[i:])   # leftovers
        out.extend(right[j:])
        return out
# O(n log n) time, O(n) space.

    def merge(self, intervals: List[List[int]]
              ) -> List[List[int]]:
        intervals.sort(key=lambda iv: iv[0])
        out = []
        for start, end in intervals:
            if out and start <= out[-1][1]:
                # overlaps the last one
                out[-1][1] = max(out[-1][1], end)
            else:
                out.append([start, end])
        return out

Interesting fact: Timsort: the sort inside Python

When you call sorted(), Python runs Timsort. Tim Peters wrote it for Python in 2002. It's a mix of merge sort and insertion sort, built for real data, which is often partly sorted already.

Timsort first looks for runs: stretches of the list that are already in order (or in reverse order, which it flips). Then it merges the runs, like merge sort. On a list that is already sorted it just checks it in one pass, O(n).

It worked so well that others copied it. Java uses Timsort to sort lists of objects (since Java 7), Android uses it, and Chrome's V8 JavaScript engine switched Array.prototype.sort to Timsort in 2018.

Recursion

Read first: Arrays: one loop does a lot

Recursion is when a function calls itself on a smaller piece of the problem. It sounds like a trick, but it is the natural way to handle things that contain smaller copies of themselves: trees, folders, and many puzzles.

The idea

Think of Russian dolls. You open a doll and find a smaller doll inside. You open that one, and there's an even smaller one. You stop when you reach the tiniest doll, the one that doesn't open.

A recursive function works the same way. Every recursive function needs two rules:

  1. A base case: the tiniest doll. A small input where you know the answer straight away, so the function stops calling itself.
  2. A smaller step: every other call works on a smaller input than the one it was given, so it gets closer to the base case each time.

Forget rule 1 or rule 2 and the function calls itself forever (until Python gives up with an error).

Example: add up a list. The sum of [3, 1, 2] is "the first number, plus the sum of the rest". The sum of an empty list is 0. That's the base case.

Calls go down until the base case. Then the answers come back up, one level at a time. Python remembers each waiting call on the call stack, a stack of unfinished calls: the last call to start is the first to finish.

In Python

def total(nums):
    # 1. base case: empty list
    if not nums:
        return 0
    # 2. smaller step: the rest of the list
    return nums[0] + total(nums[1:])

def countdown(n):
    if n == 0:          # base case
        print("Go!")
        return
    print(n)
    countdown(n - 1)    # smaller step

How to write one without getting lost. Don't try to follow every call in your head. Instead, make a leap of faith: assume the smaller call already works. For total: "if total(nums[1:]) gives me the sum of the rest, what do I do with it?" Add the first number. Done. Then check the base case. That's all.

The recursion limit. Python allows about 1000 calls waiting at once. A list of 5000 items in total crashes with RecursionError. For long lists, a plain loop is safer. Recursion shines when each call goes only a few levels deep, like halving a number or walking a tree.

Worked example: Fibonacci

The Fibonacci numbers are 0, 1, 1, 2, 3, 5, 8, … Each one is the sum of the two before it. That's already a recursive rule:

def fib(n):
    # base cases: fib(0) = 0, fib(1) = 1
    if n < 2:
        return n
    # two smaller calls
    return fib(n - 1) + fib(n - 2)

The fix: remember each answer the first time you compute it. This is called memoisation. Python does it for you with @cache:

from functools import cache

@cache   # remembers every fib(n) it has seen
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

Now each fib(k) is computed only once, so fib(n) takes O(n) time instead of exponential time. "Recursion + remember the answers" has a name: dynamic programming. It gets its own lessons later.

Binary trees: depth-first

Read first: Recursion, Linked lists

A binary tree is like a linked list where each node can point to two next nodes instead of one. Depth-first search walks it by going all the way down one branch before trying the next, and recursion makes that only a few lines long.

The idea

Think of a family tree drawn upside down: one person at the top, their children below, their grandchildren below that. A binary tree is the same, but every person has at most two children, a left one and a right one.

A few words you will see everywhere:

  • Node: one box in the tree. It holds a value and two links, left and right. A missing child is None.
  • Root: the node at the top. You are given only the root, just like you are given only the head of a linked list.
  • Child: a node directly below another one. Leaf: a node with no children.
  • Depth (or height) of a tree: how many nodes are on the longest path from the root down to a leaf.

Depth-first means: from a node, go down the left branch as far as it goes, come back, then go down the right branch. You finish a whole branch before you start the next one.

The trick is that every child is the root of a smaller tree (a subtree). So a tree problem splits into the same problem on the left subtree and on the right subtree. That's recursion's "smaller step". The base case is the empty tree, None.

In Python

LeetCode gives you this class (it's in a comment above your code):

class TreeNode:
    def __init__(self, val=0,
                 left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

Almost every depth-first solution has the same shape:

def solve(node):
    # 1. base case: the empty tree
    if node is None:
        return ...
    # 2. leap of faith: solve each side
    left = solve(node.left)
    right = solve(node.right)
    # 3. combine them with this node
    return ...

Each node is visited once, so it takes O(n) time for n nodes. The waiting calls take O(h) space, where h is the depth of the tree.

Pre-order, in-order, post-order. These three names only say when you look at the node itself: before both subtrees, between them, or after them.

def walk(node, out):
    if node is None:
        return
    # pre-order: node first
    out.append(node.val)
    walk(node.left, out)
    # in-order: node in the middle
    walk(node.right, out)
    # post-order: node last

Move the out.append line to one of the three spots. For the tree above you get:

Notice the in-order result is sorted. That's no accident: this tree is a binary search tree, the topic of a later lesson.

Without recursion. Recursion uses Python's call stack. You can use your own stack instead. Pre-order: pop a node, record it, push its right child, then its left child (so the left one is popped first).

def preorder(root):
    out = []
    stack = [root] if root else []
    while stack:
        node = stack.pop()
        out.append(node.val)
        # push right first,
        # so left comes out first
        if node.right:
            stack.append(node.right)
        if node.left:
            stack.append(node.left)
    return out

Handy for very deep trees, where recursion would pass Python's limit of about 1000 calls.

Worked example: maximum depth

The depth of a tree is 1 (for the root) plus the depth of its deeper subtree. The empty tree has depth 0.

def max_depth(node):

        return 0
    left = max_depth(node.left)
    right = max_depth(node.right)

Binary trees: level by level

Read first: Binary trees: depth-first, Queue and deque

Breadth-first search (BFS) visits a tree one row at a time: the root, then all its children, then all the grandchildren. It's the right tool whenever a question says "per level", "nearest" or "shortest".

The idea

In the depth-first lesson you went all the way down one branch before trying the next. Breadth-first is the other way round. Think of reading a family tree generation by generation: first the grandparent, then every parent, then every child, left to right.

A level is one row of the tree. The root is level 1, its children are level 2, and so on. Here is the tree from the last lesson. BFS reads it as 4, then 2 7, then 1 3 6 9.

How do you remember who's next? With a queue: first in, first out, like the queue at a shop. Each step:

  1. Take the node at the front of the queue.
  2. Look at it (record its value, check it, whatever the problem asks).
  3. Add its children to the back of the queue.

Because children always join behind everyone already waiting, a whole level leaves the queue before the next level starts. Here is the queue for our tree, at the start of each level:

LevelQueue (front first)What happens
14take 4, add 2 and 7
22 7take 2, add 1 3; take 7, add 6 9
31 3 6 9take each leaf, add nothing
endemptydone

Notice: at the start of each level, the queue holds exactly that level. That's the key to the template below.

In Python

Use deque from the queue lesson. popleft() takes from the front, append() adds to the back.

from collections import deque

def levels(root):
    if root is None:
        return []
    out = []
    queue = deque([root])
    while queue:
        # queue holds exactly one level
        size = len(queue)
        row = []
        for _ in range(size):
            node = queue.popleft()
            row.append(node.val)
            if node.left:
                queue.append(node.left)
            if node.right:
                queue.append(node.right)
        # one whole level is done
        out.append(row)
    return out

The trick is size = len(queue) before the inner loop. The children you add during the loop belong to the next level, and the loop stops before reaching them. For our tree this returns [[4], [2, 7], [1, 3, 6, 9]].

Each node goes into the queue once and out once: O(n) time. The queue holds at most one level, which can be about half the nodes: O(n) space.

BFS or DFS?

Both visit every node, so for many problems either works. Pick BFS when the question is about:

  • Levels: "the average of each row", "the rightmost node of each row".
  • Nearest or shortest: "the closest leaf to the root". BFS meets nodes in order of distance from the root, so the first match is the nearest one and you can stop early. DFS might wander down a very long branch first.

Pick DFS (recursion) when the answer for a node is built from the answers of its subtrees, like depth or "same tree".

Interesting fact: A garbage collector that walks breadth-first

Languages like Java and JavaScript free unused memory for you with a garbage collector. One classic design, published by C. J. Cheney in 1970, copies every object that is still in use into a fresh area of memory and throws the old area away.

Cheney's algorithm finds those objects breadth-first: copy the objects the program points to directly, then the objects they point to, and so on. The clever bit: the fresh memory area is the queue. One pointer marks the next copied object to look at (the front), another marks where the next copy goes (the back). When the two meet, the queue is empty and the work is done, with no extra memory for a queue at all.

The idea is still used for the "young generation": the area where new, mostly short-lived objects live. V8, the JavaScript engine in Chrome and Node.js, cleaned its young generation with Cheney's algorithm until 2017 (V8 6.2), when it switched to a parallel copying collector that spreads the same job over several threads.

Remember

  • BFS = queue: take from the front, add children to the back. Level by level.
  • Template: for _ in range(len(queue)): handles exactly one level.
  • Use BFS for "per level" and "nearest / shortest" questions; it can stop at the first match.

Binary search trees

Read first: Binary trees: depth-first, Binary search

A binary search tree keeps its values in order, so you can find any value by going left or right at each node, like binary search. It is a normal binary tree with one extra rule.

The idea

Think of a librarian sorting returned books. At each shelf there is a sign: "before M go left, after M go right". At the next shelf there is another sign. You never look at the whole library, you just follow the signs.

A binary search tree (BST) works the same way. The rule, for every node:

  • everything in its left subtree is smaller than it;
  • everything in its right subtree is bigger than it.

To find 6: start at the root 8. 6 is smaller, so go left to 3. 6 is bigger, so go right. Found it. Each step throws away a whole subtree, just like binary search throws away half of a list.

Two more things follow from the rule:

  • In-order is sorted. In-order (left, node, right, from the depth-first lesson) visits all the smaller values, then the node, then the bigger ones. For the tree above: 1 3 6 8 10 14.
  • The shape matters. A search takes one step per level, so it costs O(h), where h is the height of the tree. A nice bushy tree has about log n levels. But insert 1, 2, 3, 4 in that order and every new value goes to the right. The "tree" becomes a linked list, and a search costs O(n).

A balanced tree has about the same height on the left and right of every node. To build one from a sorted list, pick the middle value as the root, then do the same for the left half and the right half. You will do exactly this in problem 108 below.

In Python

Nodes are the same TreeNode class as before. Search is a simple loop, no recursion needed:

def search(node, target):
    while node:
        if target == node.val:
            return node
        # smaller: go left
        if target < node.val:
            node = node.left
        # bigger: go right
        else:
            node = node.right
    # fell off the tree: not there
    return None

Insert walks the same path and hangs the new node where the walk falls off the tree:

def insert(node, val):
    # empty spot: put the node here
    if node is None:
        return TreeNode(val)
    if val < node.val:
        node.left = insert(
            node.left, val)
    else:
        node.right = insert(
            node.right, val)
    return node

Both take O(h) time: about O(log n) if the tree is balanced, O(n) if it is a chain.

LeetCode530. Minimum Absolute Difference in BST
Easy ~10 min☐ solved · https://leetcode.com/problems/minimum-absolute-difference-in-bst/
Hint

Solution
class Solution:
    def getMinimumDifference(
        self, root: Optional[TreeNode]
    ) -> int:
        prev = None
        best = float("inf")

        def walk(node):
            nonlocal prev, best
            if node is None:
                return
            walk(node.left)
            # values arrive sorted here
            if prev is not None:
                gap = node.val - prev
                best = min(best, gap)
            prev = node.val
            walk(node.right)

        walk(root)
        return best

Heaps

Read first: Sorting

A heap is a pile that always hands you its smallest item first. You can add and remove items quickly, and you never have to sort the whole thing.

The idea

Think of A&E at a hospital. Patients do not wait in arrival order. The nurse always calls the most urgent patient next, even if they came in five minutes ago. New patients arrive all the time, and each one slots in by urgency.

A heap does this with numbers. It answers one question fast: "what is the smallest item right now?" A heap where the smallest is on top is a min-heap. One with the biggest on top is a max-heap.

  • Look at the smallest: O(1), it is always at the top.
  • Add an item, or remove the smallest: O(log n).

Sorting the list again after every change would cost O(n log n) each time. A heap only keeps things "roughly" in order: just enough to know who is on top.

A heap is a binary tree with one rule: every parent is smaller than (or equal to) its children. So the root is the smallest of all. Left and right are not in order, unlike a binary search tree.

The clever part: the tree is stored in a plain list, row by row. No node objects, no pointers. The tree above is just this list:

The children of the item at index i sit at 2*i + 1 and 2*i + 2. Its parent is at (i - 1) // 2. Check: the children of index 1 (value 3) are at 3 and 4 (values 7 and 4).

How it stays a heap:

  1. Add: put the new item at the end of the list. While it is smaller than its parent, swap them. It "bubbles up".
  2. Remove the smallest: take the root. Move the last item to the root. While it is bigger than a child, swap it with the smaller child. It "sinks down".

Each swap moves one level, and the tree has about log n levels. That is where O(log n) comes from.

In Python

You never write those swaps yourself. Python's heapq module does them on a normal list. It is a min-heap.

import heapq

heap = []
heapq.heappush(heap, 5)
heapq.heappush(heap, 1)
heapq.heappush(heap, 3)
# smallest, without removing: 1
heap[0]
# remove and return smallest: 1
heapq.heappop(heap)

# turn a whole list into a heap
# in place, in O(n)
nums = [4, 7, 2, 9]
heapq.heapify(nums)

There is no max-heap in heapq. The trick: push negative numbers. The smallest negative is the biggest number. Flip the sign back when you pop.

heap = [-x for x in [4, 7, 2]]
heapq.heapify(heap)
# biggest: 7
biggest = -heapq.heappop(heap)

You can also push tuples, like (priority, name). Python compares them by the first item, then the second if there is a tie.

The "top k" pattern. To keep the k biggest items you have seen, keep a min-heap of size k. When it grows to k + 1, pop the smallest. The k items left are the biggest ones, and heap[0] is the k-th biggest. Each step costs O(log k).

def k_largest(nums, k):
    heap = []
    for x in nums:
        heapq.heappush(heap, x)
        # too many: drop the smallest
        if len(heap) > k:
            heapq.heappop(heap)
    # heap[0] is the k-th largest
    return heap

Easy ~10 min☐ solved · https://leetcode.com/problems/last-stone-weight/
Hint

Solution
class Solution:
    def lastStoneWeight(
        self, stones: List[int]
    ) -> int:
        # negate: heapq is a min-heap
        heap = [-s for s in stones]
        heapq.heapify(heap)
        while len(heap) > 1:
            a = -heapq.heappop(heap)
            b = -heapq.heappop(heap)
            # a >= b. Keep what is left.
            if a != b:
                heapq.heappush(
                    heap, -(a - b))
        if heap:
            return -heap[0]
        return 0
# O(n log n) time, O(n) space.

        heapq.heappush(self.heap, val)
        # keep only the k biggest
        if len(self.heap) > self.k:
            heapq.heappop(self.heap)
        # smallest of the k biggest
        return self.heap[0]

Greedy choices

Read first: Sorting

A greedy algorithm always takes the choice that looks best right now, and never goes back to change it. When it works, it is the simplest and fastest solution there is.

The idea

You work at a shop till and owe a customer 68p. You don't think hard. You grab the biggest coin that still fits, again and again: 50p, then 10p, then 5p, 2p, 1p. Five coins, and that is the fewest possible.

That is a greedy algorithm. At each step it makes the best-looking local choice (the choice that is best for this one step). It never undoes a choice. It hopes the local choices add up to the best answer overall.

Careful: they don't always. Imagine a country with only 1p, 3p and 4p coins, and you owe 6p.

  • Greedy takes 4p first, then 1p, then 1p: three coins.
  • The best answer is 3p + 3p: two coins.

Taking the 4p looked good, but it was a trap. So greedy needs a reason to be right. Before you trust it, ask yourself one question:

"Is there ever a reason NOT to take this choice now?"

With British coins, the answer is no: a big coin never blocks a better answer. With 1p, 3p, 4p, the answer is yes. When the answer is yes, you need a different tool (dynamic programming solves the coin problem for any coins).

Here is a greedy rule from the problem Lemonade Change below. Lemonade costs $5. A customer pays with $20, so you owe $15. Which notes do you give back?

Why use the $10 first? A $5 can help with any later change. A $10 can only help with a $20. So keeping $5 notes is never worse. Nothing makes you want to hold on to the $10.

In Python

Most greedy solutions have the same shape. Sort first (see Sorting), so the best choice is always next in line. Then make one pass, taking each choice as it comes.

def make_change(amount, coins):
    # biggest coin first
    coins = sorted(coins, reverse=True)
    used = []
    for c in coins:
        # take this coin while it fits
        while amount >= c:
            amount -= c
            used.append(c)
    return used

make_change(68, [1, 2, 5, 10, 20, 50])
# [50, 10, 5, 2, 1]
make_change(6, [1, 3, 4])
# [4, 1, 1]: not the best!

Cost: the sort is O(n log n), and the pass after it is usually O(n). So most greedy solutions are O(n log n) overall, with almost no extra memory.

Interesting fact: Greedy inside every ZIP file

In 1952, David Huffman, then a student at MIT, found a way to give each symbol (say, a letter) a code made of bits. Common symbols get short codes, rare ones get long codes, so the whole file gets smaller.

Huffman coding is a core part of DEFLATE, the compression used by ZIP and gzip files and inside PNG images (its spec is RFC 1951). Baseline JPEG photos use Huffman coding too.

Bit tricks

Read first: Big O in plain words

Inside the computer, every number is a row of 0s and 1s called bits. A few small tricks with bits solve some problems in one line, with no extra memory.

The idea

Picture a row of light switches. Each switch is worth a number: from the right, 1, 2, 4, 8, and each next one is worth double. A switch that is on is a 1. A switch that is off is a 0. Add up the switches that are on, and you get the number.

So 13 is 1101 in binary (numbers written with only 0 and 1). Python shows it with bin:

bin(13)    # '0b1101'
bin(5)     # '0b101'
int("101", 2)  # 5, back again

The 0b at the front only means "this is binary".

The operators

Bit operators look at two numbers switch by switch, lined up from the right:

  • a & b (AND): 1 where both are 1.
  • a | b (OR): 1 where either is 1.
  • a ^ b (XOR): 1 where they are different.
  • a << 1: slide every bit one place left. That doubles the number.
  • a >> 1: slide every bit one place right. That halves it (rounding down).
aba & ba | ba ^ b
00000
01011
10011
11110

Three tricks

You only need three tricks for the problems below.

1. Pairs cancel: x ^ x == 0. A number XOR itself has no different bits, so it is 0. And x ^ 0 == x. Order does not matter. So if you XOR a list where every number appears twice except one, the pairs vanish and the lonely number is left:

2. Drop the lowest 1: x & (x - 1). Taking 1 away flips the lowest 1-bit to 0 and every 0 to its right to 1. AND keeps only what both share, so the lowest 1 disappears:

x = 12       # 1100
x - 1        # 1011
x & (x - 1)  # 1000 = 8

3. Odd or even: x & 1. The switch worth 1 is the only odd one. So x & 1 is 1 for odd numbers and 0 for even ones.

In Python

Here are the tricks as a small toolbox you can copy:

def lonely(nums):
    # every number twice but one
    ans = 0
    for x in nums:
        # pairs cancel out
        ans ^= x
    return ans

def count_ones(x):
    count = 0
    while x:
        # drop the lowest 1-bit
        x &= x - 1
        count += 1
    return count

def is_odd(x):
    return x & 1 == 1

lonely([5, 3, 5])   # 3
count_ones(13)      # 3 (1101)
is_odd(13)          # True

Cost: lonely is one pass, O(n) time and O(1) space. count_ones loops once per 1-bit. A LeetCode number has at most 32 bits, so that is O(1).

Math tricks

Read first: Counting things

Some problems are about numbers themselves: their digits, their remainders, their sums. A few small tricks turn them from puzzles into a few lines of code.

The idea

Think of a car's mileage counter. The right-most wheel shows the last digit. In Python you get it with n % 10: the remainder after dividing by 10. To throw that digit away, use n // 10: divide by 10 and drop the part after the point.

Do both again and again until the number is 0, and you visit every digit, from the right:

Modulo means wrap around. % is called modulo. Think of a clock: 3 hours after 11 o'clock is 2 o'clock, not 14. That is (11 + 3) % 12 == 2. The answer always stays between 0 and 11. Two handy uses:

  • n % 2 == 0: n is even.
  • n % 3 == 0: n divides by 3 with nothing left over.

Spot a loop with a set. Some problems repeat a step on a number: "replace n by the sum of the squares of its digits". Either you reach the goal, or you come back to a number you have seen before. Then you are stuck in a cycle (a loop that never ends). Keep every number you see in a set (see Hash maps and sets). If a number shows up twice, stop.

The set costs memory. The fast and slow pointers trick from Linked lists finds the same loop with O(1) memory: one number takes one step at a time, the other takes two, and if there is a loop they meet.

Look for a formula first. Before you write a loop, ask if maths already has the answer. The sum 1 + 2 + … + n is n * (n + 1) // 2. For n = 4: 4 × 5 / 2 = 10, and indeed 1 + 2 + 3 + 4 = 10. One line instead of a loop.

In Python

def digits(n):
    # digits of n, right to left
    out = []
    while n > 0:
        # last digit
        out.append(n % 10)
        # drop it
        n //= 10
    return out

def has_loop(n, step):
    # repeat step until we see
    # a number again (or reach 1)
    seen = set()
    while n != 1 and n not in seen:
        seen.add(n)
        n = step(n)
    return n != 1

def sum_to(n):
    # 1 + 2 + ... + n
    return n * (n + 1) // 2

digits(472)    # [2, 7, 4]
(11 + 3) % 12  # 2
sum_to(4)      # 10

Cost: a number n has about log10(n) digits, so digits is O(log n), which is tiny: even a billion has only 10 digits. sum_to is O(1): one sum, no loop.

Interesting fact: The digit check on your bank card

The last digit of a credit or debit card number is a check digit. It is chosen so that a small digit sum, the Luhn algorithm, comes out right. Shops and websites run it before sending the number anywhere, so a typo is caught at once.

How it works: from the right, double every second digit. If a doubled digit is over 9, take 9 away. Add up all the digits. The number is valid if the total ends in 0, that is total % 10 == 0.

It catches every single mistyped digit, and almost every swap of two neighbouring digits (only 09 ↔ 90 slips through). It is named after Hans Peter Luhn of IBM, who filed the patent "Computer for verifying numbers" in 1954 (US patent 2,950,048). Today it is part of the ISO/IEC 7812 standard for card numbers.

Graphs: BFS and DFS

Read first: Binary trees: level by level, Hash maps and sets

A graph is a set of places joined by connections: stations and tracks, people and friendships, pixels and their neighbours. Learn to walk a graph and a huge family of problems opens up.

The idea

Look at the Tube map. Each station is a node (a place). Each stretch of track between two stations is an edge (a connection). That is all a graph is. Here are five stations in central London (some stops in between are left out):

You already know one kind of graph: a tree. A tree is a graph with no loops. Graphs can have loops: Waterloo → Westminster → Embankment → Waterloo. That one difference matters a lot. If you walk a graph the way you walk a tree, you go round that loop for ever.

The fix is a visited set (see Hash maps and sets). Before you step onto a node, check: "have I been here?" If yes, skip it.

Storing a graph. Problems usually give you a list of edges, like [[0, 1], [1, 2]]. Turn it into an adjacency list: a dict from each node to the list of its neighbours. "Adjacent" just means "next to".

Grids are graphs too. A grid of cells (an image, a map of land and sea) is a graph where each cell's neighbours are the cells up, down, left and right. No need to build a dict: you work out the neighbours from the row and column.

Walking a graph works just like trees:

  1. DFS (depth-first): go as deep as you can, then back up. Use recursion or a stack.
  2. BFS (breadth-first): visit everything 1 step away, then 2 steps, and so on. Use a queue.

Both mark each node as visited the moment they reach it.

In Python

from collections import defaultdict
from collections import deque

def build(edges):
    # node -> list of neighbours
    graph = defaultdict(list)
    for a, b in edges:
        # undirected: both ways
        graph[a].append(b)
        graph[b].append(a)
    return graph

def bfs(graph, start):
    visited = {start}
    queue = deque([start])
    while queue:
        node = queue.popleft()
        for nxt in graph[node]:
            if nxt not in visited:
                visited.add(nxt)
                queue.append(nxt)
    return visited

def dfs(graph, node, visited):
    visited.add(node)
    for nxt in graph[node]:
        if nxt not in visited:
            dfs(graph, nxt, visited)

Cost: every node is visited once and every edge is looked at twice (once from each end). With V nodes and E edges that is O(V + E) time, and O(V) memory for the visited set and the queue.

On a grid, the neighbours of cell (r, c) are:

for dr, dc in ((1, 0), (-1, 0),
               (0, 1), (0, -1)):
    nr, nc = r + dr, c + dc
    # stay inside the grid
    if (0 <= nr < rows
            and 0 <= nc < cols):
        ...

Backtracking

Read first: Recursion

Backtracking is a way to try every possible choice, one step at a time, and undo a step when it leads nowhere. Use it when a problem says "list all the ways": all subsets, all orders, all paths.

The idea

Picture a maze. You walk down a path. At a fork, you pick one way. If you hit a dead end, you step back to the last fork and try the next way. You keep going until you have tried every way from every fork.

That "step back" is the whole trick. In code, every step has three parts:

  1. Choose: add one item to the path you are building.
  2. Explore: call the function again (recursion) to make the next choice.
  3. Un-choose: remove that item again, so the path is clean for the next option.

Example: list all subsets of [1, 2]. A subset is any group you can pick from the list, including none of it. For each number you have two choices: take it or skip it. Draw every choice and you get a decision tree:

Each leaf (a box at the bottom) is one answer. Backtracking walks this tree depth-first: down the left side, back up, then down the next branch, just like DFS on a tree.

In Python

def subsets(nums):
    result = []
    path = []

    def go(i):
        # base case: all decided
        if i == len(nums):
            # save a copy of the path
            result.append(path[:])
            return
        # option 1: take nums[i]
        path.append(nums[i]) # choose
        go(i + 1)            # explore
        path.pop()           # un-choose
        # option 2: skip nums[i]
        go(i + 1)

    go(0)
    return result

subsets([1, 2])
# [[1, 2], [1], [2], []]

Two details trip everyone up:

  • Save a copy: path[:], not path. There is only one path list, and it changes all the time. Save the list itself and every answer ends up empty.
  • Every append needs a pop. After the "take" branch finishes, the path must look exactly as it did before.

Cost. A list of n numbers has 2n subsets (each number doubles the count), and copying each one takes up to n steps: O(n · 2n). That is exponential, and it's fine here: when the problem asks for all the answers, there simply are that many. That's why these problems keep n small (often 10 or less).

Worked example

Watch path while subsets([1, 2]) runs:

SteppathSaved

take 2, end[1, 2][1, 2]
pop 2, skip 2, end[1][1]
pop 1, skip 1[ ]
take 2, end[2][2]
pop 2, skip 2, end[ ][ ]

The path grows and shrinks like a stack. When the function finishes, it is empty again.

Dynamic programming: 1D

Read first: Recursion, Hash maps and sets

Dynamic programming (DP) is recursion that remembers the answers it has already worked out. It turns problems that take forever into one quick pass over a list.

The idea

Imagine someone asks you "what is 1 + 1 + 1 + 1 + 1?" You count: 5. Now they add "+ 1" at the end. You don't count again from the start: you remember 5 and say 6. That is DP: build big answers from small answers you saved.

You met the problem in the Recursion lesson: plain fib(n) computes the same small values again and again. Here is the same thing with a staircase. You climb 1 or 2 steps at a time. How many ways are there to reach step n?

To stand on step 4, your last move came either from step 3 (a 1-step) or from step 2 (a 2-step). So:

ways(4) = ways(3) + ways(2)

Draw the calls and you see the waste:

With a memory, ways(2) is worked out once. The second time, we just look it up. Each step is computed only once, so the cost drops from exponential to O(n).

There's an even simpler way to see it. Instead of starting at the top and going down, start at the bottom and go up. Fill a list called dp, left to right. Each box is the sum of the two boxes before it:

Box i is dp[i]: the number of ways to reach step i. dp[5] is 8.

The 3 questions

Every DP problem in this lesson is solved by answering three questions in words before writing code:

  1. What does dp[i] mean? Stairs: "the number of ways to reach step i".
  2. How does it come from smaller answers? Stairs: dp[i] = dp[i-1] + dp[i-2], because the last move was 1 step or 2 steps.
  3. What are the first values? Stairs: dp[0] = 1 (stay where you are: one way) and dp[1] = 1.

Once the three answers are clear, the code almost writes itself.

In Python

Two ways, same idea. Top-down: write the recursion and add @cache, which saves every answer (a hash map from input to answer, built for you).

from functools import cache

@cache
def ways(i):
    # first values
    if i <= 1:
        return 1
    # last move: 1 step or 2 steps
    return ways(i - 1) + ways(i - 2)

Bottom-up: fill the list from small to big. No recursion, so no depth limit.

def ways(n):
    dp = [0] * (n + 1)
    # first values
    dp[0] = 1
    if n >= 1:
        dp[1] = 1
    for i in range(2, n + 1):
        dp[i] = dp[i - 1] + dp[i - 2]
    return dp[n]

Look: dp[i] only needs the last two boxes. So keep just two numbers:

def ways(n):
    # a = dp[i-2], b = dp[i-1]
    a, b = 1, 1
    for _ in range(n - 1):
        a, b = b, a + b
    return b

Cost. All three versions do one pass over the steps: O(n) time. The first two keep n saved answers: O(n) space. The last one keeps two numbers: O(1) space.

LeetCode746. Min Cost Climbing Stairs
Easy ~15 min☐ solved · https://leetcode.com/problems/min-cost-climbing-stairs/
Hint
Question 1: dp[i] = the cheapest cost to reach step i. The top is step len(cost). Question 2: you came from step i-1 (and paid cost[i-1]) or from step i-2 (and paid cost[i-2]). Take the min. Question 3: you may start on step 0 or 1 for free.
Solution
class Solution:
    def minCostClimbingStairs(
        self, cost: List[int]
    ) -> int:
        n = len(cost)
        # dp[i]: cheapest way to reach i
        dp = [0] * (n + 1)
        # dp[0] = dp[1] = 0: free start
        for i in range(2, n + 1):
            one = dp[i-1] + cost[i-1]
            two = dp[i-2] + cost[i-2]
            dp[i] = min(one, two)
        # the top is step n
        return dp[n]
# O(n) time. Keep only two numbers
# to get O(1) space.
LeetCode198. House Robber
Medium ~20 min☐ solved · https://leetcode.com/problems/house-robber/
Hint
Stretch. Question 1: dp[i] = the most money from the first i houses. Question 2: for house i you either skip it (keep dp[i-1]) or rob it (its money plus dp[i-2], since the house next to it is off limits). Take the max. Question 3: no houses, no money.
Solution
class Solution:
    def rob(
        self, nums: List[int]
    ) -> int:
        # best from houses before the
        # last one, and up to the last
        prev2, prev1 = 0, 0
        for money in nums:
            rob = prev2 + money
            skip = prev1
            prev2, prev1 = (
                prev1, max(rob, skip))
        return prev1
# One pass: O(n) time, O(1) space.
Interesting fact: How TeX breaks a paragraph into lines

TeX is the typesetting program behind LaTeX, which many scientists use to write papers. Its source code calls line breaking "probably the most interesting algorithm of TeX".

A simple program fills each line with as many words as fit, then moves on (that's greedy). Sometimes this leaves one line full of ugly wide gaps. TeX instead looks at the whole paragraph and picks the set of breaks that looks best overall. It was designed by Donald Knuth and Michael Plass, and described in their 1981 paper "Breaking Paragraphs into Lines".

It works the DP way: for each possible break point, TeX keeps the best way to lay out the text up to there, built from the best answers for earlier break points. The paper shows this is the same as finding a shortest path through a network of break points, which is also how it avoids trying every combination.

  • DP = recursion that remembers: add @cache, or fill a dp list from small to big.
  • 3 questions: what does dp[i] mean, how does it come from smaller answers, what are the first values?
  • If dp[i] only needs the last two values, keep two variables: O(1) space.
